### 1. Problem Statement
Financial institutions receive thousands of consumer complaints monthly, but tracking them in spreadsheets or email inboxes causes regulatory response deadlines to be missed and systemic company failures to go unnoticed. The CFPB received over 2.7 million credit reporting complaints in 2024 alone (a 106% increase from the previous year). Manual tracking cannot scale to enforce deadlines or detect patterns. ComplaintGuard solves this by using PL/SQL to automatically calculate deadlines, enforce resolution logging, and flag non-compliant companies.

### 2. Proposed Solution
ComplaintGuard is an Oracle PL/SQL database system. When a complaint is logged, a trigger automatically calculates its regulatory deadline based on the product category. Another trigger blocks users from closing a complaint unless a resolution is recorded. A nightly scheduled job runs a procedure to flag complaints nearing their deadline and to identify companies with high volumes of unresolved complaints. An Oracle APEX dashboard will provide compliance managers with a live view of urgent complaints and company patterns.

### 3. Data Source
**Dataset:** Complaint Tracking and Analytics Dashboard Dataset
**Link:** https://www.kaggle.com/datasets/chinmayprakash12/complaint-tracking-and-analytics-dashboard-dataset
**Size:** 100,000 records (English).
**Privacy:** Anonymized; contains no personally identifying information.
*Note:* The dataset simulates real-world banking complaints. Deadline rules will be stored in a configurable lookup table so they can be adjusted to match actual regulatory frameworks (like Rwanda's).

### 4. Planned Tables
- **COMPANIES:** Company identifiers.
- **PRODUCT_CATEGORIES & ISSUE_TYPES:** Lookup tables for classification.
- **COMPLAINTS:** Core table storing the complaint, dates, and calculated deadline.
- **RESOLUTIONS:** Tracks the exact action taken to close the complaint.
- **DEADLINE_ALERTS:** Stores alerts generated by the system for near-breach complaints.
- **COMPANY_PATTERNS:** Precomputed table for unresolved complaint counts.
- **AUDIT_LOG:** Tracks all INSERT/UPDATE/DELETE operations.

### 5. Planned PL/SQL Features (Aligning with Course Modules)
- **Functions:** `fn_calculate_deadline` (returns the response deadline based on category and receipt date).
- **Procedures:** `sp_log_complaint`, `sp_close_complaint`, `sp_flag_approaching_deadlines`, `sp_company_pattern_report`.
- **Packages:** `pkg_complaintguard` to encapsulate related procedures and functions, improving modularity.
- **Cursors:** An explicit cursor in the nightly job to loop through open complaints and generate alerts for those past the deadline.
- **Triggers:** 
  - A *BEFORE INSERT* trigger calculates and sets the response deadline.
  - A *BEFORE UPDATE* trigger blocks status changes to 'CLOSED' if no resolution exists.
  - An *Audit trigger* logs every change.
- **Exceptions:** Custom exceptions like `e_no_resolution_recorded` to handle business rule violations gracefully.

### 6. Innovation
**Option:** User Interface + Smart Automation.
**Tools:** Oracle APEX (Dashboard) + DBMS_SCHEDULER.
**How it works:** The APEX dashboard connects directly to the Oracle database. It calls `pkg_complaintguard` procedures to log and close complaints, and displays real-time data from the `DEADLINE_ALERTS` and `COMPANY_PATTERNS` tables. A `DBMS_SCHEDULER` job runs nightly to automate the pattern detection and alert generation, ensuring the database acts on its own without manual SQL intervention.
